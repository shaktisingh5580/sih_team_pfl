# 0. The Problem Statement — What ISRO Actually Asks

> **PS Title:** Design and Develop an Intelligent Conversational Platform for Marine Ecosystem Data Exploration and Decision-Making

> **PS ID:** 26176 | **Organization:** ISRO / Department of Space

## 0.1 The Exact PS Description (Preserved)

> The marine ecosystem plays a vital role in supporting livelihoods, food security, biodiversity, maritime transportation, coastal resilience, and the blue economy. Every day, vast volumes of satellite Earth Observation and oceanographic data, including Sea Surface Temperature (SST), chlorophyll concentration, and weather forecasts, are generated by ISRO and other global agencies.
>
> Marine stakeholders such as fishermen, researchers, coastal authorities, disaster management agencies, and maritime operators rely on timely access to oceanographic and meteorological information for operational planning and decision-making. As the volume, diversity, and complexity of marine data continue to increase, there is a growing need for an intelligent conversational platform that enables users to interact naturally with marine information, ask questions, explore scenarios, and receive synthesized, evidence-based recommendations tailored to their context.
>
> Advances in Agentic AI, conversational intelligence, and large language models (LLMs) make it feasible to build systems that can interpret user queries, identify relevant datasets, retrieve and analyze marine data, and provide actionable insights — all through natural dialogue, interactive maps, and dynamic visual dashboards.

## 0.2 The PS Example Queries (Must-Demo)

The PS explicitly lists these example user queries:

```text
1. "Where is the nearest Potential Fishing Zone (PFZ) today?"
2. "Is it safe to venture into the sea tomorrow morning?"
3. "What are the tide, weather, and sea conditions near my fishing location?"
4. "Are there any lightning or cyclone alerts in my area?"
5. "Which regions show high chlorophyll concentration and favourable SST for fish aggregation?"
6. "What is the safest route from port A to port B, considering weather and sea conditions?"
7. "Why has fish productivity declined near [coastal area] in recent months?"
8. "Which fishing zones should be avoided due to hazardous conditions?"
```

> [!CAUTION]
> Every one of these 8 queries must work in the demo. Not with hardcoded data — with real investigation.

# 1. The Core Realization

The PS does **not** ask us to build a marine data platform that happens to have an AI chatbot.

It asks us to build:

> **An autonomous conversational investigation system that happens to use marine data.**

The architecture, the demo, and the code should all tell this story:

```text
USER asks a hard marine question
      ↓
ORCA autonomously investigates
      ↓
Multiple agents collaborate on evidence
      ↓
Evidence is correlated across sources
      ↓
A decision is made with full reasoning
      ↓
The user sees chat + map + charts + alerts
```

Everything else — data pipelines, databases, connectors — is the **engine underneath**, not the product itself.

# 3. The Hero Investigation Loop

This is the single most important thing in the entire system — the core product:

```text
                    ASK
                     ↓
                 UNDERSTAND
             (intent + context)
                     ↓
                    PLAN
          (task decomposition)
                     ↓
              DISCOVER DATA
       (catalog search + selection)
                     ↓
           SELECT TOOLS / AGENTS
                     ↓
                  EXECUTE
            ┌────────┼────────┐
            ▼        ▼        ▼
          OCEAN   WEATHER    GEO
            └────────┼────────┘
                     ▼
                CORRELATE
          (multi-source fusion)
                     ↓
              OBSERVE STATE
          (is evidence sufficient?)
                     ↓
           ┌─────────┴─────────┐
           │                   │
      ENOUGH?                 NO
           │                   │
          YES               REPLAN
           │                   │
           │             MORE EVIDENCE
           │                   │
           └──────────←────────┘
                     ↓
                  DECIDE
                     ↓
                 EXPLAIN
          (evidence chain + reasoning)
                     ↓
           ┌─────────┼──────────┐
           ▼         ▼          ▼
         CHAT       MAP       CHART
                     │
                     ▼
                   ALERT
```

> [!IMPORTANT]
> This loop must be **visible to the user** during the demo. The user should see ORCA thinking, planning, fetching, correlating, and reasoning — not just returning an answer.

# 4. Two Execution Modes

### 4.1 Reactive Mode (User Asks)

```text
User question → Investigation → Response
```

### 4.2 Proactive Mode (System Monitors)

```text
Monitoring rule → New marine condition detected
     ↓
Data retrieval → Risk analysis → Validation
     ↓
Alert pushed to user
```

Both modes must exist. The PS explicitly requires proactive alerts for weather, cyclones, lightning, and geofencing.

# 9. Context-Aware Responses

The same data should produce different responses for different stakeholders:

| Stakeholder | Same Wind + Wave Data → Different Response |
|-------------|---------------------------------------------|
| **Fisherman** | "Winds are 15 km/h. Safe for your boat. Return before afternoon." |
| **Port Operator** | "Wind 15 km/h. No impact on port operations. Vessel movements normal." |
| **Researcher** | "Wind anomaly: +4 km/h above September climatology. Correlated with SST shift." |
| **Coastal Authority** | "No coastal flood risk. Wave height within design limits." |

# 10. Scenario Exploration (Multi-Turn)

```text
User:  "Is it safe to go tomorrow at 6 AM?"
```

# 20. Mock Mode and Golden Datasets (Phase 0 Requirement)

> A hackathon demo should NEVER depend on perfect internet/API availability.

```text
LIVE MODE  - uses real external sources (INCOIS, IMD, Copernicus, etc.)
MOCK MODE  - uses cached/frozen golden data
```

Implementation:

```text
ORCA_DATA_MODE=live    -> real API calls
ORCA_DATA_MODE=mock    -> golden dataset responses
```

# 25. Scientific Language Contract

> These rules apply to ALL user-facing text generated by ORCA.

### Safety Wording

```text
DO NOT: "It is safe."
DO:     "Available evidence indicates LOW operational risk
         for the requested time window."

DO NOT: "Safety scoring engine"
DO:     "Operational Risk / Suitability Engine"

DO NOT: "It is MODERATELY SAFE to fish"
DO:     "Conditions assessed as MODERATE OPERATIONAL RISK"
```

### Causal Wording

```text
DO NOT: "SST caused the productivity decline."
DO:     "The SST change is associated with the observed decline
         and is consistent with known mechanisms."

DO NOT: "explain causal factors with evidence"
DO:     "identify contributing factors supported by evidence"
```

### PFZ Wording

```text
DO NOT: "Fish will be here."
DO:     "PFZ advisory indicates favorable conditions for
         fish aggregation in this zone."
```

### Forecast Wording

```text
DO NOT: "This will happen."
DO:     "The forecast indicates..."
```

### Route Wording

```text
DO NOT: "This is the safest route."
DO:     "This route has the lowest assessed risk under the
         selected objectives and constraints."
```

### HAB Wording

```text
high chlorophyll != confirmed HAB
```

# 30. Regional Language Architecture (PS Requirement — P0)

> The PS explicitly requires: automatic language identification, same-language response, Indian regional languages.

### Language Flow Through Memory

```text
User asks in Gujarati
        |
        v
Language detected = Gujarati
        |
        v
Memory / Context
preferred_response_language = Gujarati
        |
        v
Planner
        |
        v
Agents (work in English internally)
        |
        v
Evidence (structured, language-independent)
        |
        v
Response Synthesizer
        |
        v
Gujarati response
```

### V1 Demo Languages (minimum)

```text
English     - full support
Hindi       - full support  
Gujarati    - full support (primary demo persona)
```

### Implementation

```text
Language detection:  LLM-based (no separate NLP model needed)
Translation:         LLM generates response directly in target language
Memory:              preferred_language stored as USER_PREFERENCE in memory_items
Context:             Language preference injected into every Context Packet
Response:            Synthesizer generates in detected/preferred language
```

